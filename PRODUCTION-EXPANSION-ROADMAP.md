# ꙰ SHIRMANI Production Expansion Roadmap

## Production-first rule

Automation is used to **produce customer-visible work**, not to make verification the primary workload.

Pipeline:

**INSTITUTE → FACTORY → QC/GATE → PUBLIC SHOWROOM → CUSTOMER EXPERIENCE → REVIEW → IMPROVEMENT → NEXT PRODUCTION CYCLE**

## Current state

- Published concrete product batch: **1,016**
- Product families: **25**
- Published QC metadata: product ID + QC code + gate + dispatch state
- Public showroom: active
- Public payment routes: **Paytm/UPI + PayPal**
- Current automated expansion target: **5,000 concrete product assets**
- Commercial settlement: not claimed complete until transaction evidence exists
- Independent scientific verification: downstream and separate from production

## Expansion stages

1. **5,000** concrete products — immediate automated expansion target.
2. **10,000** — after the 5,000-product deployment remains stable.
3. **50,000** — after storage, build time, navigation and customer usability remain healthy.
4. **100,000+** — staged production with indexing and partitioned catalogues.
5. **Million-scale** — only with suitable storage, deployment, search/indexing and delivery infrastructure; do not create a false claim merely from a counter.

## Customer-visible requirement

A product should resolve to a real public artifact with:

- product ID
- category
- description
- price / offer where approved
- product route
- QC metadata
- gate state
- dispatch state
- customer-facing usage or delivery route

Workflow execution alone is never counted as a product.

## Continuous operation

The public production Automission remains scheduled every 5 minutes. The expanded target is configured through `PRODUCT_TARGET`, so the factory can grow in controlled stages without changing the production principle.

## Funding use

Funding is intended to increase:

- concrete product production
- useful module depth
- hosting/storage capacity
- public showroom quality
- customer delivery infrastructure
- security and reliability
- review-driven product improvement

Payment routes published by this project are limited to the configured Paytm/UPI and PayPal routes. Users must verify the payee and amount in their own payment application before sending money.

## Integrity boundary

“Produced”, “QC-passed”, “sold/settled”, and “independently verified” are different states. This separation protects the public customer interface from unsupported claims while keeping production moving continuously.
