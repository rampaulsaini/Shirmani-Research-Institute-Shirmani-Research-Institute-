# Actual Platform Execution Plan — 2026-10-05

## Purpose

This document separates **workflow activity** from **real platform capability**.

A successful GitHub Actions run proves that an automated check or job executed. It does not, by itself, prove that the public platform is production-ready, that an external service is operating, that a research claim is independently verified, or that income/settlement occurred.

## Completion rule

A layer is considered **ACTUAL / OPERATIONAL** only when its concrete external or runtime behavior can be demonstrated and its evidence is preserved.

## Multi-layer execution stack

| Layer | Current direction | ACTUAL exit evidence |
|---|---|---|
| Public interface | GitHub Pages + research dashboards | User-visible route works from an external browser; key actions and status states are truthful |
| Research intake | Source → claim → evidence pipeline | A real source enters the pipeline and produces traceable records without invented IDs |
| Evidence | Review packets + verification ledger | Human/independent review records exist; automation cannot manufacture VERIFIED |
| AI / NLP | v3 validation, abstention, provenance | Measured evaluation results, calibration/error reports, adversarial tests, and explicit abstention |
| Automation | Factory / supervisors / watchdogs | Automation performs useful bounded work and records artifacts, not just successful runs |
| Production runtime | Application/runtime services | External endpoint, persistence, HTTPS/security, monitoring, rollback and recovery evidence |
| Data persistence | Records / ledgers / archives | Durable storage survives a fresh run and can be reconstructed from recorded evidence |
| Product layer | Research/archive products | At least one complete user-facing workflow goes from input to usable output |
| Income layer | Income-first architecture | A real offer, delivery path, payment/settlement evidence and reconciliation exist |
| Governance | Nishpaksh boundaries | Claims, hypotheses, creative statements and verified findings remain explicitly separated |

## Immediate execution priority

1. **Runtime reality:** identify and close the gap between static GitHub Pages/code and a continuously usable application service.
2. **Evidence reality:** move from prepared packets/queues to concrete reviewed records, without automated VERIFIED creation.
3. **End-to-end product:** select one narrow user workflow and make it complete from public input to useful delivered result.
4. **Persistence:** ensure the result and provenance survive independent re-runs.
5. **Income path:** connect one real product/service delivery path to an auditable settlement/reconciliation record.
6. **Only then scale:** expand multi-agent automation after the first complete operational loop is demonstrably working.

## Fail-closed integrity boundaries

The following must never be inferred from workflow success alone:

- scientific truth;
- independent verification;
- human review;
- revenue or payment;
- production availability;
- model accuracy beyond measured evaluation;
- deployment safety.

## Progress language

Use these states consistently:

- **DESIGNED** — specification/code exists.
- **AUTOMATED** — workflow can execute a check or transformation.
- **INTEGRATED** — components exchange real artifacts end-to-end.
- **OPERATIONAL** — an external/runtime behavior is demonstrable.
- **VERIFIED** — independent evidence supports the specific claim; automation must not create this state.

The goal of the next phase is therefore not more workflow count. It is to convert **DESIGNED/AUTOMATED → INTEGRATED → OPERATIONAL**, while preserving the independent-verification boundary.
