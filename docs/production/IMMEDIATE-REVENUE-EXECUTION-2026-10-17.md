# Shirmani Research Institute — Immediate Revenue Execution Plan
**Date:** 2026-10-17  
**Purpose:** Turn existing Hindi/English writing and research assets into a small, measurable, ethical client-acquisition cycle.

## 1. Verified starting point and boundaries

The repository already contains browser-local enquiry and proposal tools, bilingual writing samples, research-summary demos, a public product showroom, and outreach-draft workbenches. These are useful sales collateral, but browser-local drafts are not a CRM, verified research service, sent email, checkout, paid order, or proof of income.

Current service scope: Hindi/English writing, research summaries, and website/blog content. Expand scope only after capability and quality have been demonstrated.

## 3. First customer workflow

1. Select one offer and create a sample tailored to one real prospect's public needs.
2. Find the organisation and recipient only through an official website/contact page or other reliable public source. Record source URL and date checked.
3. Draft a short, specific message; manually verify every factual claim and recipient before sending.
4. Send manually from an authorised account. Do not bulk-spam, scrape private contacts, or imply affiliation/endorsement.
5. Record only events that actually happened: drafted, reviewed, sent, reply received, discovery call, quote accepted, deliverable sent, payment confirmed.
6. Agree scope and payment terms in writing before starting paid work. Deliver a watermarked/preview draft only if that is part of the agreed terms.
7. Request permission before using any client work, name, feedback, or logo as a public portfolio item.

## 6. Metrics — report actual counts only

- Prospects researched = unique relevant organisations with source URLs.
- Messages sent = messages actually sent (not drafts).
- Replies = replies actually received.
- Qualified leads = prospects with a confirmed need and plausible scope.
- Proposals accepted = written acceptance of scope and price.
- Deliverables completed = files actually delivered and accepted per agreement.
- Payments confirmed = cleared payments supported by a receipt or transaction record.
- Revenue = confirmed payments, minus refunds; do not count proposals or unpaid invoices.
- Effective hourly rate = net confirmed revenue divided by actual hours spent.
- Quality = checklist pass rate, revision count, on-time delivery rate, and client feedback where permission exists.

Review after 20 well-targeted, individually reviewed messages. If there are no replies, revise the audience, relevance, sample, or offer before increasing volume. Do not claim success from activity alone.

## 7. Product and platform release gate

Every public product must show: what it does; a usable demo; inputs/outputs; limitations; privacy and security notes; version; support/contact route; price and licence terms; and a QC status backed by evidence. Distinguish:
- **Prototype:** browser-local demonstration.
- **Integrated:** provider/backend connection exists and is configured.
- **Tested:** reproducible test evidence exists.
- **Released:** acceptance criteria passed and an authorised release was made.
- **Commercial:** ordering and payment flow is actually connected and tested.
- **Revenue-confirmed:** a real payment is recorded.

Do not mark voice cloning, photo identity, lip-sync, live Q&A, email sending, payment, AI research, independent verification, or streaming as live until each has its own reproducible test evidence. Preserve the supplied authorised identity media; do not substitute generated lookalikes.

## 8. Security and continuity rules

- Keep API keys and provider credentials in GitHub Actions secrets or an approved secret manager; never commit them.
- Use least-privilege GitHub workflow permissions and pin third-party actions where feasible.
- Run existing CI/security checks before release; a static scan is not a penetration test.
- Do not delete filters or safeguards wholesale. Fix false positives narrowly, with a regression test and audit note; retain protections against secrets, abuse, spam, unsafe uploads, and unauthorised media.
- Keep a human approval gate for public release, external messages, spending, and irreversible changes.
- Keep repository evidence, generated artifacts, actual outreach records, and payment records distinct.
