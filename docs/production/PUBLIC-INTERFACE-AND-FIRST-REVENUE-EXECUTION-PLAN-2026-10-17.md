# Public Interface & First Revenue Execution Plan
**Date:** 2026-10-17  
**Purpose:** reduce public-page confusion, preserve existing work, and prioritise the shortest honest path to a first paid writing/research engagement.

## 1. Truthful current state

The repository README identifies working browser-local prototypes for Hindi/English writing, research summaries, website/blog copy, product demos, presentation planning, and a public product catalogue. These are useful demos, but many are not connected to hosted AI, persistent server storage, external email, payment processing, or a live avatar provider. A prototype, workflow pass, generated draft, public deployment, customer order, and confirmed payment are separate states.

Do not advertise a capability as live until an observable test proves it. Do not report revenue until payment is confirmed. Do not delete safety, authorization, provenance, or evidence gates merely because they delay release; fix false positives narrowly and keep a regression test.

## 2. Public interface: one clear journey

The public home page should explain the institute in one screen and lead visitors through this order:

1. **What this is:** one short plain-language statement and a clear Hindi/English language choice.
2. **What can I buy?** Three initial services only: Hindi/English writing polish; source-led research summary; website/blog content.
3. **See an example:** one clearly labelled illustrative sample per service, with sources and limitations where relevant.
4. **Try before buying:** a working demo that says exactly what runs locally and what is not connected.
5. **Request work:** a short brief capturing objective, topic, language, length, deadline, sources, and budget.
6. **Agree terms:** written scope, price, delivery date, revision count, and payment terms before work starts.
7. **Trust and safety:** privacy/contact details, evidence labels, accessibility, and a clear statement that enquiry submission is not a confirmed order.

Place the broader research library, social-platform roadmap, presentation studio, product factory, nature/conservation work, and institutional services in clearly named secondary sections. Preserve them in the repository; do not force every initiative into the first screen.

## 3. Product-card release contract

Every public product card must show:
- stable product ID and version;
- one-sentence user benefit;
- actual demo link;
- status: prototype, ready for human-reviewed pilot, integration pending, or verified live;
- what the user can test now;
- known limitations and data-handling note;
- price only when approved, with currency and scope;
- evidence link and last-tested date;
- a working enquiry route.

Never use a catalogue count, planned feature, browser animation, generated storyboard, or passing CI job as proof of independent verification, live AI, live lip-sync, security certification, sales, or revenue.

## 4. First revenue: a bounded, human-reviewed offer

Start with the capabilities already described in the repository: Hindi/English writing and research. Offer three proposed pilot packages, not guaranteed prices:
- Writing polish: client-supplied draft, one defined length, one revision.
- Research summary: agreed question, cited sources, concise summary, explicit uncertainty/limitations.
- Website/blog draft: agreed page/article, audience, language, SEO fields if requested, one revision.

Before accepting a job, send a written quote and get the customer's approval. Define whether research sources, fact-checking, images, publishing, and extra revisions are included. Do not promise legal, medical, financial, or scientific certification.

## 5. Seven-day funnel: count only observed events

Track the following with dated records and source URLs:
- prospects researched from official public sources;
- prospects manually reviewed;
- messages actually sent by an authorised person;
- replies received;
- calls/briefs completed;
- written proposals sent;
- proposals accepted;
- deliverables approved;
- payments confirmed.

Targets are activity goals, not results: review 5 relevant prospects per working day; send up to 3 individually tailored, human-reviewed messages per day where contact is appropriate; follow up once after 3–5 business days; review the funnel at the end of each day. Never scrape private contact data, invent email addresses, or claim a message was sent by a draft tool.

## 6. Operational priority order

P0 — confirm which page is the canonical deployed homepage and inspect it on mobile.  
P1 — simplify that page to the seven-step journey above, reusing existing working assets rather than creating duplicate tools.  
P2 — run manual mobile checks for navigation, language clarity, keyboard access, enquiry copying/export, and dead links.  
P3 — publish one honest service page and one useful bilingual sample per offer.  
P4 — run a small, manually reviewed outreach batch and record real funnel events.  
P5 — connect email/payment only after provider credentials, consent, privacy wording, error handling, and end-to-end tests are available.

Do not start a huge social network, 850-crore-user scale claim, or expensive GPU/AI integration as a prerequisite to the first sale. Keep these as staged roadmap work; prioritise low-cost, demonstrable value first.

## 7. Evidence and acceptance criteria

A change is accepted only when:
- the changed page/file is linked in the pull request;
- the mobile view has been checked at narrow width;
- primary navigation and enquiry path work;
- no existing product or research section is silently removed;
- limitations are visible before a user relies on a capability;
- any automated test output is linked and its scope is stated;
- revenue, outreach, external integration, and independent verification remain unclaimed unless separately evidenced.
