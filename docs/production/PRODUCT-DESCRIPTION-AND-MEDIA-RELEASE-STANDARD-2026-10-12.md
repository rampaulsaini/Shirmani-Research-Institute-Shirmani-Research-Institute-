# SHIRMANI Product Description Standard — 2026-10-12

## Purpose
Improve product descriptions first, before claiming new product media or integrations are complete. Every public listing must let a beginner understand what the tool does, who it is for, how to try it, what it produces, what it does not do, and how to enquire.

## Description hierarchy

1. **Product identity:** stable ID, distinct name, version, category and release state.
2. **On-image short description:** one plain-language sentence, ideally 12–20 words; describe a real user outcome, not a superlative.
3. **Who it helps:** identify the intended user and the problem being addressed.
4. **How to use:** three to five numbered steps, including a sample input and expected output.
5. **Outputs and supported inputs:** concrete files, fields or actions that the current version actually supports.
6. **Evidence and limitations:** distinguish working features from templates, storyboards, planned integrations and externally dependent features.
7. **Media:** product-specific cover image, scannable QR linking to the full passport, real demo video, and real VIP screenshot. Until an asset exists, display a clear “Not yet created” label; never substitute a brief or storyboard while calling it a finished asset.
8. **Commercial terms:** visible price or “quote after scope confirmation”, deliverables, revision policy, delivery time and payment terms.
9. **Quality loop:** version/date, test status, feedback route, issue and improvement log.

## Required evidence labels
- **VERIFIED:** an explicit test result or other adequate independent evidence is linked.
- **SOURCE-BASED:** a source is linked, but independent verification is not claimed.
- **PHILOSOPHICAL / IDENTITY:** personal viewpoint or identity language, not presented as scientific evidence.
- **INSUFFICIENT EVIDENCE:** say “अभी पर्याप्त प्रमाण उपलब्ध नहीं है।”

## Copy rules
- Prefer short, concrete Hindi and English; define technical terms in everyday words.
- Avoid unsupported terms such as “world's best”, “unbreakable”, “100% accurate”, “quantum-powered”, “live AI”, “unique invention”, or “guaranteed income”.
- Do not describe a template as connected AI, a storyboard as an MP4, a QR preview as a scannable QR, or a screenshot brief as a captured screenshot.
- State clearly when a tool runs locally in the browser and does not send data, email prospects, accept payments, or save to a server.
- Preserve the owner's supplied portrait exactly when an authorized original image asset is available; allow resizing/cropping only when it does not alter facial identity. Do not synthesize a replacement portrait or voice.
- Use the exact authorized voice only after the asset is supplied and integration/consent tests pass.

## Product-card release checklist
- [ ] Stable product ID, version and current release state
- [ ] Distinct product name and concise on-image description
- [ ] Owner's original portrait/logo asset linked and visually checked
- [ ] Product-specific QR generated from the correct canonical passport URL and scanned on mobile
- [ ] Full product passport with features, instructions, supported inputs/outputs and limitations
- [ ] Actual demo video linked; otherwise label “Storyboard only — video not recorded”
- [ ] Actual VIP screenshot linked; otherwise label “Screenshot not captured”
- [ ] Mobile readability and image scaling checked
- [ ] Price/quote basis, scope, delivery, revision and payment terms visible
- [ ] QC evidence, last-tested date, feedback route and version history
- [ ] No claim of sale, outreach, income, integration or verification without evidence

## Release states
- **DISCOVERY:** problem and user not yet scoped.
- **BUILDING:** prototype or draft exists.
- **QC_BLOCKED:** one or more required checks/assets are missing or failing.
- **QC_PASSED:** stated tests passed and evidence is linked.
- **PUBLISHED:** owner-approved listing is public, with accurate readiness labels.

A successful workflow run alone does not move a product to QC_PASSED or PUBLISHED.
