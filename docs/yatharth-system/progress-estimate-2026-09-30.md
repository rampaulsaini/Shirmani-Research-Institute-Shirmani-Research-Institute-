## Overall engineering estimate

For the **software/platform implementation program only**, a reasonable current planning estimate is **about 30–35% complete**, with a midpoint of **~33%**.

This number is a planning indicator derived from the current feature-status dimensions and weighted by implementation maturity. It is **not** a scientific measurement and must not replace the dimension-specific status registry.

The remaining **~65–70%** is mainly real implementation, integration, production hardening, security/privacy, payments, external services, public user flows, monitoring, and human-review processes—not merely more documentation.

## What is already substantial

- Canonical Yatharth source and claim lifecycle are structured.
- Evidence/counter-evidence and independent-verification boundaries are defined.
- Research Factory and repository automation are active.
- Public-platform contracts, status registry and fail-closed release gates exist.
- Public status/continuity entry points exist.
- Governance architecture has explicit human authority, appeal and safety boundaries.
- Independent verification is intentionally kept at **0** until qualifying independent human review exists.

## Approximate time from the 2026-09-30 state

These are planning ranges, not guarantees.

### A. Public working MVP
**~2–4 months** with sustained daily engineering and AI-assisted development.

Target: public accounts, core content/research UI, creator publishing, initial AI assistant, basic marketplace/store flows, status dashboard, monitoring and security baseline.

### B. Broad integrated platform
**~4–8 months**.

Target: stronger AI/ML/NLP services, Automission federation, research/evidence UI, education, jobs/freelancing, creator economy, music/media, payments and operational hardening.

### C. Mature multi-domain ecosystem
**~8–18+ months**.

Target: reliable production operations, stronger security/privacy, scalable integrations, mature community systems, robust governance/appeal tooling, measured environmental programs and repeatable independent-review processes.

### D. Independent verification

No fixed completion date should be promised. It depends on the availability, scope, quality and decisions of genuinely independent qualified reviewers and evidence. Software automation can prepare packets and route work, but it cannot manufacture independent verification.

## Recommended operating rule

Continue in parallel rather than waiting for one giant final release:

**Implement → Test → Security/Privacy Review → Monitor → Release a small usable capability → Record evidence → Improve → Repeat.**

This keeps the platform useful while preventing documentation, workflow success or AI output from being mistaken for production deployment or independent verification.
