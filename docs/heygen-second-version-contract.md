# SHIRMANI Second Version — HeyGen / Live Presentation Contract

## Purpose

This contract defines the presentation layer for a future HeyGen/LiveAvatar integration. It is a specification and readiness gate; it does not claim that an external HeyGen account, API key, avatar, voice, or live session is connected until independently evidenced.

## Core pipeline

Voice → authorized voice integration → content/context engine → evidence gate → Q&A → avatar/photo → lip-sync → live presentation → transcript/session audit → customer feedback → continuous improvement.

## Character requirements

The presentation must aim for:

- simple, natural, clear, transparent communication;
- natural eye contact/gaze where the selected avatar technology supports it;
- natural facial movement;
- accurate lip synchronization;
- coherent voice/face timing;
- context-aware answers;
- source-linked answers when evidence exists;
- explicit uncertainty when evidence is insufficient;
- respectful treatment of every person, caste, religion, faith, organization and community;
- separation of philosophical/identity statements from independently verified scientific claims.

## Evidence rule

The live character must never convert an identity or philosophical statement into a scientific fact merely because the user or character asserts it.

When adequate evidence exists:

**Answer → source → evidence status**

When evidence is inadequate:

**“अभी पर्याप्त प्रमाण उपलब्ध नहीं है।”**

## Voice authorization

Only a voice that the account owner is authorized to use may be integrated. The repository must store configuration references, not secret credentials.

## Camera/device independence

The mobile device used for the platform does not need to be the device used to capture the user's source video or voice. A separate device may supply authorized source media; the platform should preserve a device-independent content contract.

## Recovery / continuity

Important character definitions, prompts, approved scripts, source records, product briefs and integration decisions must be stored in the repository rather than relying on a single external chat session.

## Product integration

The presentation layer should consume the existing product pipeline:

SOURCE_ASSET → PRODUCT_RECORD → PACKAGING → PRODUCT_PAGE → CREATIVE_BRIEF → SEO_METADATA → DELIVERY_PATH → READY_FOR_REVIEW → EVIDENCE → VERIFICATION

The current repository already contains Product Media Factory, Product-Specific Demo Media, Visual/QR production and customer-review improvement workflows. This contract adds the presentation layer rather than duplicating those factories.

## Reality gate

The system must distinguish:

- configured;
- connected;
- tested;
- production-ready;
- independently verified.

A workflow run alone is never evidence that an external HeyGen operation succeeded.

## Target

Build a reusable second-version presentation subsystem that can be attached to:

1. personal introduction;
2. research/evidence Q&A;
3. product demonstrations;
4. podcast/live presentation;
5. customer support;
6. multilingual content.

The system should preserve provenance, versioning and auditability for every published presentation artifact.
